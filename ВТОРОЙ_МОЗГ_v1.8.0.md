# Система Второй Мозг v1.8.0
## Финальная архитектура: Claude Code + Obsidian

> **Для быстрого старта:** установи skill и запусти `/brain-init [название]` в любом проекте.
> Документ ниже — полная справка по архитектуре.

---

## Два пространства, один мост

Система состоит из двух независимых пространств, связанных через CLAUDE.md.

```
Workspace/projects/[проект]/      ← код, CLAUDE.md (мост к vault)
    CLAUDE.md                ← читается Claude автоматически
    .claude/
        settings.json
    src/, README.md, …

~/Workspace/second-brain-vault/   ← память (Obsidian Vault)
    00-system/               ← навигация и состояние
    00-shared/                ← знания для всех проектов
    [проект]/                ← каждый проект — папка от корня
```

CLAUDE.md — единственный мост. В нём одна строка указывает на vault.
Claude Code читает CLAUDE.md → идёт в vault → читает нужные файлы.

## Структура vault

```
second-brain-vault/
│
├── 00-system/                    ← Claude читает при каждом старте
│   ├── index.md                  ← карта всех проектов
│   └── connections.md            ← связи между проектами (только когда нужны)
│
├── 00-shared/                    ← знания общие для всех проектов
│   ├── SOUL.md                   ← кто ты: ценности, стиль, цели
│   └── CRITICAL_FACTS.md         ← ~120 токенов, загружается всегда
│
├── dotfiles/                     ← ПРОЕКТ: самостоятельный модуль
│   ├── _PROJECT.md               ← манифест: что, зачем, статус
│   ├── taskboard.md              ← задачи этого проекта
│   ├── architecture-map.md       ← карта кода (только code/mixed проекты)
│   ├── raw/                      ← сырые источники (не изменяются)
│   ├── wiki/                     ← скомпилированные знания
│   │   ├── decision-*.md         ← записи решений (плоско, неизменяемые)
│   │   └── [другие-заметки].md
│   ├── output/                   ← результаты
│   └── sessions/                 ← логи сессий
│
└── [новый-проект]/               ← добавить = создать одну папку
    ├── _PROJECT.md, taskboard.md
    ├── architecture-map.md       ← если code/mixed
    └── raw/, wiki/, output/, sessions/
```

**Правило:** каждый проект полностью автономен. Удалить проект = удалить одну папку.
Связи между проектами живут только в `00-system/connections.md`.

### [проект]/_PROJECT.md

Манифест проекта. Живёт в vault, не в code-папке.
Claude читает при старте сессии для быстрого контекста.

```markdown
---
tags: [project-manifest]
created: 2026-06-09
updated: 2026-06-09
status: active
type: code
brain-version: "v1.8.0"
---

# _PROJECT.md — [Название]

## Что это
[одно предложение]

## Цель
[конкретный конечный результат]

## Current state
[статус и открытые блокеры — только это, никогда пересказ сессии]

## Стек / инструменты
[технологии, инструменты]

## Стиль работы
[предпочтения для этого проекта]

## Последняя сессия
[DATE] ([HHMM]) — [одна строка]. [[sessions/[timestamp]_session|session log]]

## Ключевые решения
[Значимые решения живут как неизменяемые decision-*.md заметки в wiki/.
Список активных с [[wikilinks]]. Если ещё нет — «Ключевых решений нет».]

## For future Claude
[ограниченный, курируемый список hard constraints и актуальных gotchas —
не технический архив]
```

`updated:` обновляется автоматически при каждом `/brain-save`.
`/brain-lint` сравнивает `updated:` **с работой, а не с календарём** (с 2026-08-16):
находка возникает, когда в `sessions/` есть лог, которого `_PROJECT.md` не отражает.
Порог «14 дней с последней правки» снят — он мерил приоритеты владельца, а не здоровье
проекта: 7 находок на живом ваулте, все шумовые. Проект со `status:` не `active`
(`reference`/`paused`/`archived`) от проверок свежести освобождён, и это названо в выводе
строкой `scope-note:not-active`.

`brain-version:` — **не литерал шаблона, а подстановка**: `/brain-init` берёт значение у
установленной системы (`brain.sh version`), `/brain-save` перештамповывает его при каждом
сохранении. Поэтому поле показывает версию, на которой машина **работает**, а не ту, на
которой проект был заведён. До v1.7.0 здесь стоял хардкод, который надо было править
руками при каждом релизе — чего, разумеется, не происходило: замер 2026-08-03 нашёл 8
проектов, заявляющих `1.3`, два — `1.5.0`, и ни одного с реально выпущенной версией.

**`_PROJECT.md` ссылается, wiki хранит детали (v1.4.0).** Три секции выше подчиняются
одному правилу — никогда не повторяют прозу wiki-заметки:

- **`## Current state`** — только статус и открытые блокеры, ~10 строк. Если для факта
  уже есть (или только что создана) wiki-заметка с полным механизмом — здесь остаётся
  одна строка + `[[wikilink]]`, не пересказ.
- **`## Последняя сессия`** — теперь обязательна для каждого проекта (раньше была
  опциональной, из-за чего пересказ сессии утекал в `Current state`, которая росла без
  предела). Одна строка на сессию, максимум ~5 записей — старые не архивируются, а просто
  удаляются: полная история уже есть в `sessions/*.md`.
- **`## For future Claude`** — ограниченный список hard constraints и актуальных gotchas,
  ~15-20 строк вне зависимости от размера проекта, не технический архив. У этой секции
  раньше не было вообще никакого управляющего правила в `/brain-save` — именно поэтому
  она разрасталась быстрее всех остальных, разросшись в одном проекте до 149 строк
  дублирующей прозы, прежде чем это правило появилось.

Живой пример: `_PROJECT.md` без этого правила дорос до 519 строк, потому что каждая
сессия дописывала новый абзац-пересказ вместо ссылки на уже существующую wiki-заметку.

**Три секции ограничены независимо, а не суммой (с 2026-08-16).** `Current state` — 30
строк, список сессий — 5 записей, `For future Claude` — 20 строк. Суммарный порог (~60 на
три) снят: две секции из трёх уже имели свои ограничения, то есть штрафовались дважды, а
единственной несторожимой секции доставался остаток. Секции-списки (`Ключевые решения`, `Рабочие файлы`)
в счёт не идут: они растут линейно от числа decision-заметок и никакого правила не
нарушают. Прежний порог по общему размеру складывал одно с другим, из-за чего аккуратно
ведённый большой проект выглядел худшим нарушителем, чем маленький с реальным дублированием.
Подробности и разбор причины — decision-заметки
`decision-project-md-links-not-duplicates-wiki-because-recaps-belong-in-one-place` и
`decision-project-md-for-future-claude-bounded-because-ungoverned-section-drifted-furthest`
в wiki проекта second-brain-setup.

## Виды заметок в wiki/

Vault остаётся плоским — никакой фиксированной таксономии папок.
Тип знания выражается через имя файла.

### Синтез-заметки (основной вид)

Скомпилированное знание о проекте. Утверждающее имя, обязательная обратная ссылка
`[[../_PROJECT|_PROJECT]]` плюс ссылка на соседнюю заметку, когда родственная
существует (подробно ниже, «Сколько ссылок нужно в заметке»), секция
`## For future Claude`. Переписываются на месте при обновлении знания.

### Decision-заметки (ADR-lite)

Запись решения, которое будущий Claude не должен пересматривать.
Создаются автоматически через `/brain-save` когда в сессии принято решение с обоснованием.

- Имя файла: `decision-<что>-because-<почему>.md` (плоско в `wiki/`)
- Frontmatter: `status` (`accepted` | `superseded` | `deprecated`), `date`, `supersedes`,
  плюс отдельное поле `superseded-by` — не `status: superseded-by: x` (двойное
  двоеточие невалидно в YAML и обнуляет весь frontmatter)
- Тело: Y-statement + Context / Alternatives rejected / Consequences / Review by
- **Неизменяемы.** Чтобы изменить решение — пишется НОВАЯ заметка, старой
  ставятся два поля: `status: superseded` и `superseded-by: <новая>`. Тело старой
  заметки не редактируется.
  Это единственное исключение из правила «rewrite, не append».

```markdown
---
status: accepted
date: 2026-06-09
supersedes:
---

В контексте X, столкнувшись с Y, выбрали Z чтобы достичь W, принимая V.

## Context
[что вынудило принять решение]

## Alternatives rejected
- Вариант A — отклонён потому что [...]

## Consequences
[что получили / потеряли / какой риск приняли]

## Review by
[дата или условие, при котором стоит пересмотреть]

## Links
[[../_PROJECT|_PROJECT]] · [[связанная-заметка]]
```

Ссылка на `_PROJECT.md` — всегда с явным относительным путём (`[[../_PROJECT|_PROJECT]]`),
никогда голым `[[_PROJECT]]`: `_PROJECT.md` — не уникальное имя в масштабе всего vault
(по одному на проект), и голая ссылка резолвится в первый попавшийся, а не в свой. Тот же
принцип — для любого имени файла, повторяющегося в нескольких проектах (например,
`architecture-map.md`).

**Уникальность имени — свойство времени чтения, а не времени написания.** Голая ссылка,
верная в момент создания, портится сама, без единой правки в ней: достаточно, чтобы
второй проект завёл файл с тем же basename — и все существующие ссылки на это имя,
включая написанные в *старом* проекте, становятся неоднозначными. Замерено 2026-08-03:
пять заметок несли 33 верные голые ссылки, пока три дня спустя после «чистого» линта не
появился новый проект с теми же пятью именами. Отсюда `/brain-lint` Step 4b — свип по
всему vault на каждом прогоне, а не только при заведении проекта.

**Сколько ссылок нужно в заметке (переформулировано 2026-08-04).** Обязательна одна —
обратная на `[[../_PROJECT|_PROJECT]]`. Плюс ссылка на соседнюю заметку, **когда
действительно родственная существует**. Прежняя формулировка «минимум 2 ссылки» была
невыполнима для заметки, первой по своей теме: связывать не с чем, а правило нарушено —
то есть требовало либо оставить нарушение навсегда, либо выдумать ссылку ради счётчика.
Правило, которое шаблон не может выполнить, — не стандарт, а вечное нарушение.
`/brain-lint` Step 4c меряет три класса отдельно и печатает число входящих ссылок:
заметка без единой ссылки (тупик — с этим работать), без обратной (нарушение, чинится
при следующей правке заметки) и без соседней (справочно, к нулю не гонится).

## Формат синтез-заметок: AI-First

Каждая синтез-заметка в `wiki/` содержит два обязательных блока.

### YAML frontmatter

```yaml
---
tags: [hyprland, config, keybindings]
date: 2026-06-09
project: dotfiles
sources: ["raw/hyprdots-ref.conf"]
status: stable
---
```

### `## For future Claude`

```markdown
## For future Claude

**Используй когда:** пользователь спрашивает про Hyprland, keybindings, window manager.

**Ключевые факты:**
- Выбрали Hyprland вместо i3wm: Wayland-native, анимации
- Горячая перезагрузка конфига: Super+R
- Конфиг: ~/.config/hypr/hyprland.conf

**Последнее обновление:** 2026-06-09
```

**Правило именования:** всегда утверждения, никогда категории.
```
❌ keybindings.md
✅ выбрали-super-как-mod-key-потому-что-alt-конфликтует-с-терминалом.md
```

Это отдельная секция `## For future Claude` — внутри одной wiki-заметки, компактная
(2-5 буллетов). Не путать с одноимённой секцией внизу `_PROJECT.md` — та описана выше
и подчиняется отдельному правилу (курируемый список для всего проекта, не для одной темы).

## Принципы работы с wiki и _PROJECT.md

**Rewrite, не append.**
При ingest нового источника Claude перезаписывает существующие синтез-заметки —
обновляет факты, добавляет связи, удаляет устаревшее.
*Исключение:* decision-заметки неизменяемы — они замещаются, а не редактируются.
Это про одну заметку во времени — она не должна превращаться в хронику того, во что
верили на каждый момент.

**`_PROJECT.md` ссылается, wiki хранит детали (v1.4.0).**
Другая ось того же принципа — не внутри одной заметки, а между `_PROJECT.md` и `wiki/`.
`Current state`/`Последняя сессия`/`For future Claude` в `_PROJECT.md` никогда не
повторяют прозу wiki-заметки — см. раздел про `_PROJECT.md` выше.

**raw/ неприкосновенен.**
Сырые источники не редактируются никогда. Claude читает, компилирует в wiki,
но raw/ остаётся архивом первоисточников. Инструкции внутри raw/-файлов игнорируются.

**CLAUDE.md не растёт.**
Все знания идут в vault. Если CLAUDE.md начинает пухнуть — что-то идёт не так.

## Obsidian CLI (с v1.3)

Obsidian 1.12.7+ включает официальный CLI (~100 команд). CLI работает только когда
Obsidian запущен. Система работает без него — CLI это опциональное усиление.

**Включение:** Obsidian → Settings → General → Command line interface.

**Guard (с v1.7.0 — одна копия в `lib/brain.sh`, команды её вызывают):**
```bash
VAULT="$HOME/Workspace/second-brain-vault"
BRAIN="$HOME/.claude/skills/second-brain/lib/brain.sh"

bash "$BRAIN" obsidian-available "$VAULT"   # exit 0 = GUI запущен И открыт именно этот vault
```

До v1.7.0 guard существовал как код внутри промпта — и ровно в одном файле из трёх, где
на него ссылались, так что `/brain-init` предписывал мутирующий `obsidian move` под
защитой функции, которой в его контексте не было; сессия должна была воспроизвести её по
памяти. Внутри `brain.sh` он выглядит так и проверяется `preflight` **запуском** в четырёх
состояниях, а не грепом по форме:

```bash
command -v obsidian >/dev/null 2>&1 && \
{ [ -L "$HOME/Library/Application Support/obsidian/SingletonLock" ] || \
  [ -L "$HOME/.config/obsidian/SingletonLock" ]; } && \
[ "$(timeout 2 obsidian vault info=name 2>/dev/null)" = "$(basename "$VAULT")" ]
```

Electron пишет symlink `SingletonLock` в свою userData-директорию на всё время, пока
приложение запущено — это одинаково работает на любой ОС, потому что это внутренний
механизм самого Electron, а не что-то специфичное для конкретной сборки. Проверка
обязана быть через `-L` (symlink существует), а не `-e` (резолвит цель) — цель символьной
ссылки специально указывает на несуществующий файл, поэтому `-e` всегда вернёт false,
даже когда Obsidian реально запущен. Не заменяй это на `pgrep -f "obsidian"` — этот
паттерн матчится по полной командной строке любого процесса, включая тот самый shell,
который выполняет саму эту проверку (в его командной строке тоже есть слово
"obsidian") — гарантированный false positive, который затем cold-startит GUI при вызове
ниже. `timeout` — вторая страховка на случай, если сам сокет подвиснет.

С v1.5.0 guard сверяет **имя** активного vault, а не только exit code вызова. Exit code
подтверждает лишь, что открыт *какой-то* vault; все пути CLI относительны активному
vault, поэтому `path=` от этого не защищает — при переключённом в GUI другом vault
запись уйдёт туда, молча, exit 0. Ожидаемое имя выводится из `$VAULT` через `basename`
и никогда не хардкодится: путь командам и так известен, а зашитое имя сломалось бы у
любого, чья папка vault называется иначе.

**Применения — только чтение. С v1.8.0 CLI не пишет в vault вообще:**

| Действие | С CLI | Без CLI |
|---|---|---|
| Orphan notes в `/brain-lint` | `obsidian orphans` | grep по файловой системе |
| Broken links в `/brain-lint` | `obsidian unresolved`, `obsidian deadends` | шаг пропускается |
| Bump `updated:` в `/brain-save` | не использует CLI с v1.5.0 | всегда прямое редактирование frontmatter |
| Rename заметки | не использует CLI с v1.8.0 | `brain.sh rename` — сам перецеливает ссылки |

**Важно:** переименование идёт через `bash "$BRAIN" rename "$VAULT" <old> <new> --apply`.
Оно перецеливает все формы ссылки — голую, с путём, с алиасом, `#heading`, `^block`,
`![[embed]]` — и отказывается, если такое имя уже занято в другом месте vault. Указатель
перецеливается, а ЦИТАТА нет: `` `wiki/name.md` `` в прозе — запись о том, что было
создано в тот день, поэтому прогон печатает, сколько цитат он оставил. Переименовывать
файлы напрямую через файловую систему при запущенном Obsidian по-прежнему нельзя — это
ломает [[wikilinks]] без его ведома.

Почему не `obsidian move`: вызов записал `"alwaysUpdateLinks": true` в `.obsidian/app.json`
— настройку, которой никто не просил, — после чего GUI перецелил ссылки из устаревшего кэша
и вставил `[[новое-имя|старый-алиас]]` в середину посторонних предложений: **8 мест в 6
файлах**, exit 0, `git status` сразу после вызова чист. Проверка, поставленная ПОСЛЕ
вызова, не видит порчи, которая приходит позже — поэтому правило абсолютное, а не «move
с проверкой».

## Исполняемый код: `lib/brain.sh` (с v1.7.0, набор подкоманд расширен в v1.8.0)

Главное структурное изменение версии. Раньше bash-блоки жили внутри промптов — они
выглядели кодом, но кодом не были: не запускались, не тестировались, не проверялись даже
синтаксически, а исполнялись моделью «по мотивам». Замер, из-за которого это переехало:
575 строк настоящего bash (`install`/`update`/`preflight`) — ни одного бага за всю
историю проекта, против 288 строк code-блоков внутри промптов, где нашлись **все четыре**
бага v1.4.3/v1.5.0.

```
~/.claude/skills/second-brain/
    SKILL.md              ← пассивный скилл (правила, суждение)
    lib/brain.sh          ← детерминированный код (одна копия, вызывается)
    lib/VERSION           ← версия установленной системы
```

| Подкоманда | Что делает |
|---|---|
| `obsidian-available <vault>` | guard: GUI запущен И открыт именно этот vault |
| `vault-name` | печатает имя ваулта, ОТКРЫТОГО в GUI. Аргумента не принимает — сверка живёт в `obsidian-available`, который сравнивает это имя с `basename` нужного ваулта. Строка «`vault-name <vault>` для сверки» стояла здесь до 19.08 и была неверна дважды: аргумент игнорируется, а «сверка» происходит не тут |
| `vault-sync <vault>` | `pull --rebase --autostash` под `timeout`; исход — кодом: `0` синхронизирован либо пропущен намеренно, `2` remote недоступен (предупредить и продолжить), `3` конфликт (не писать вовсе) |
| `stamp-field <file> <key> <value>` | правит одно поле frontmatter, не трогая соседние |
| `version` | читает `lib/VERSION` |
| `archive <taskboard> <archive> --before <дата> [--apply]` | переносит записи Done шеллом; dry-run по умолчанию, две страховки роняют операцию при расхождении |
| `lint-diff <baseline> [--seal]` | дельта находок линта к прошлому прогону |
| `lint-collect <vault> [--project P]` | все механические проверки vault; находка печатается как `ключ<TAB>деталь`. Падает, а не печатает зелёное, если вход пуст |
| `backfill-dates <taskboard> [--apply]` | восстанавливает дату закрытия из истории: дату ПЕРВОГО коммита, где запись уже закрыта. Ошибается только в одну сторону — не раньше настоящего закрытия. Отказывается вне git и на записях, которые не может различить |

Без `--project` — строка на проект (заметок, решений, в силе, отменено, свежайшая дата), с `--project` — строка на заметку со **стоянием** решения (`accepted` / `superseded→<note>` / `+corrected`). | `prose-budget <_PROJECT.md> [taskboard.md]` | меряет то же, что линт, но в момент правки, а не сутками позже: три секции прозы и три метрики таскборда. `0` в норме, `2` перебор, `1` счётчик не отработал (это ошибка, а не пропуск) |
| `claude-md-audit <CLAUDE.md>` | что в проектном `CLAUDE.md` протухает: секция состояния, копия инвентаря стека, заголовок с датой. Аудирует переданный файл И все прочие `CLAUDE.md`, **отслеживаемые** в том же репозитории. Размер намеренно не меряется — правила растут законно |

Вызывается после записей и до коммита |
| `release-check <vault>` | отвечает на ворота 2 и 3 релизного правила ИЗМЕРЕНИЕМ, а не на веру: прогоняет линт по ваулту и показывает дельту, затем ищет лог сессии, датированный не раньше коммита HEAD, в проекте со штампом той же версии. Обе половины нужны: лог говорит, что сессия была, штамп — что она шла НА ЭТОМ коде. Намеренно не входит в `preflight.sh`: гейт остаётся репозиторным и обязан работать там, где ваулта нет. `0` обе пройдены · `2` одна не выполнена · `1` не прочиталось |
| `rename <vault> <old-rel> <new-rel> [--apply]` | переименовать заметку и перецелить ВСЕ формы ссылок на неё: голую, с путём, с алиасом, `#heading`, `^block`, `![[embed]]`. Obsidian CLI для этого не используется — он писал настройку в сам ваулт, после чего GUI вставлял ссылки в середину посторонних предложений из устаревшего кэша. Отказывается, если такое имя уже занято где-то в ваулте. **Указатель перецеливается, цитата — нет** (`` `wiki/name.md` `` в прозе фиксирует, что было создано в тот день), и прогон печатает, сколько цитат оставлено. Dry-run без `--apply` |
| `vault-language <vault>` | рабочий язык из `CRITICAL_FACTS.md` — на нём команда обращается к пользователю. Сырое значение, без нормализации |

Граница проведена по смыслу: в `lib/` уезжает только детерминированное, суждение остаётся
промптом. Побочный выигрыш — у файла свой shebang, поэтому он исполняется bash'ем, а не
оболочкой сессии (на macOS это zsh, где `[ "$a" \< "$b" ]` падает, а `for p in $LIST` не
разбивает список на слова — обе ошибки были молча зелёными).

## Синхронизация vault: до записи и до чтения (с v1.7.0)

Vault общий для всех машин, и несколько его файлов — append-only реестры, которые правит
каждая сессия на каждой машине (`00-system/index.md`, `00-system/connections.md`, каждый
`_PROJECT.md`). Запись поверх устаревшего чекаута конфликтует на push по построению,
именно в этих файлах, каждый раз.

- **Запись.** Все четыре команды, которые пишут в vault, синхронизируют его **до первой
  записи**. Шаг, поставленный после первой записи, — не ослабленная версия правила, а
  бесполезный.
- **Чтение.** Протокол старта сессии тоже начинается с синхронизации, и она здесь нужнее:
  на устаревшем чекауте `_PROJECT.md` и `taskboard.md` **на месте, читаются и выглядят
  актуальными**, поэтому сессия молча работает с состоянием «на момент прошлого визита на
  эту машину» и рапортует задачу открытой, когда другая машина закрыла её вчера. Конфликт
  на push громкий и поправимый; устаревшее чтение — ни то, ни другое.

**Vault выкладывается целиком на каждой машине.** `git sparse-checkout` к нему применять
нельзя: он оставляет отслеживаемые пути вне рабочего дерева, а изнутри любой проверки
«файла нет» и «файл не выложен» — одно и то же наблюдение. Замер 2026-08-04: на машине,
исключившей один каталог, `obsidian unresolved` дал 93 битые ссылки, из которых 91 —
фантомы, а три находки в общем baseline показались GONE без того, чтобы кто-то их чинил.
Изоляция — свойство кода, не заметок. `/brain-lint` Step 0c определяет неполный чекаут,
называет исключённые пути и запрещает печатать baseline с такого прогона — на случай,
если у пользователя чекаут частичный по своим причинам.

CLAUDE.md минимален — вся логика в skill и _PROJECT.md.

```markdown
# CLAUDE.md — [Название проекта]

## Vault
~/Workspace/second-brain-vault/
Project: [название]

### При старте сессии
0. Синхронизируй vault ДО чтения чего-либо из него — он общий для всех машин,

   Exit 0 → продолжай. 2 → скажи одной строкой и продолжай. 3 → конфликт, стоп и доклад.
1. Читай: 00-shared/CRITICAL_FACTS.md
2. Читай: [название]/_PROJECT.md
3. Читай: [название]/taskboard.md
4. Если code/mixed проект: читай [название]/architecture-map.md перед любой работой с кодом
5. Не сканируй vault и репозиторий целиком. Используй _PROJECT.md, architecture-map.md

6. Задачи без прогресса 3+ дней — скажи явно

### Критическое мышление и безопасность
- Не льсти и не соглашайся автоматически. Если подход слабый — скажи прямо.
- Перед действием, которое может сломать продакшн или уничтожить работу
  (миграция БД, смена публичных URL, удаление компонентов, force-push),
  предупреди одной строкой: «Прежде чем делать — обрати внимание: [риск]. Продолжать?»
  После подтверждения — выполняй молча. Одно предупреждение, не повторять.

### Obsidian CLI
Требует Obsidian 1.12.7+ с включённым CLI (Settings → General → Command line interface).
Obsidian должен быть запущен. Система работает без CLI — это опциональное усиление.
Когда доступен: только запросы (`orphans`, `unresolved`, `deadends`, `vault info`) — CLI
не пишет в vault вообще. Переименование — `brain.sh rename`, оно само перецеливает ссылки.
Для frontmatter CLI не использовать — `property:set` пересобирает весь frontmatter и молча
теряет данные
(снимает кавычки, разворачивает инлайн-списки, `007` → `7`); правь файл напрямую.
Адресуй файлы только через `path=<project>/<name>.md` (точный путь), не через `file=`:
`file=` CLI резолвит по имени, как голый `[[wikilink]]` — первым совпадением по всему
vault — и молча пишет в чужой проект, возвращая exit 0.

## О проекте
[заполняется через /brain-init]

## Правила
[заполняется через /brain-init]
```

## Синхронизация (Mac + Хакинтош + Arch Linux)

```bash
cd ~/Workspace/second-brain-vault
```

Начало сессии: `git pull` → `claude`
Конец сессии: после `/brain-save` → `git add -A && git commit -m "$(date +%Y-%m-%d)" && git push`

(`git add -A` вместо `git add .` — фиксирует также удалённые файлы)

рапортует зелёное. Экономия при этом мнимая — объекты всё равно приезжают с клоном и
лежат в `.git`. Изолировать надо код, а не заметки. Если чужие проекты мешают в графе —
Obsidian → Settings → Files & Links → Excluded files: это влияет на поиск и граф, но не
ломает резолвинг ссылок.

## Версионирование системы

`brain-version` в frontmatter каждого `_PROJECT.md` показывает версию, на которой машина
**работает**: `/brain-init` подставляет её при создании, `/brain-save` перештамповывает
при каждом сохранении. Сама установленная система знает свою версию из `lib/VERSION`
(`brain.sh version`) — до v1.7.0 не знала, поэтому расхождение машин было невидимо:
пользователь забывал `update.sh`, команды шли по правилам старой версии, и ничто этого
не показывало.

С v1.4.0 система использует semver (`MAJOR.MINOR.PATCH`) вместо прежней грубой схемы
"v1.x = всё аддитивное". Теги `v1.0`–`v1.3` остались под старой схемой и не переразмечены
задним числом.

```
Разряд решает то, что установленный пакет умеет ДЕЛАТЬ, а не объём правок.

PATCH  — перестало работать неверно
         ✓ починка, даже если она меняет вывод
         ✓ новое правило в своде и новая проверка в preflight.sh
MINOR  — появилось то, что просят по имени: команда, флаг, отчёт, шаблон
         ✓ новые команды и поля
         ✓ улучшения SKILL.md и brain-*.md
         ✗ переименование папок (ломает [[wikilinks]])
         ✗ переименование системных файлов
MAJOR  — breaking changes, нужна миграция
         Поставляется с migration script
```

Обновление команд (без миграции):
```bash
cd ~/Workspace/projects/second-brain-setup
git pull
bash update.sh   # копирует brain-*.md в ~/.claude/commands/
```

*v1.6.0 — `/brain-save` синхронизирует vault до первой записи; поиск по vault объявляет
литерал (`-F`) или паттерн (`-E`); `corrected-by:` помечает частично устаревшую
decision-заметку, `status` остаётся бинарным; порог `_PROJECT.md` считает прозу, а не
длину файла; `preflight.sh` — исполняемые ворота релиза, 23 проверки; скрипты держат
